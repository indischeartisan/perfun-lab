# Simple Operations v1.1: staging and release review

Status: historical staging procedure, retained for reference. The owner subsequently chose a direct production rollout only after a verified restorable backup, schema/history review and passing CI. No migration, deployment or authenticated browser result is implied by this document. Follow `STAGING_PREVIEW.md` if a separate staging project is used in the future.

## Isolation and migration gate

1. Obtain an explicitly separate non-production Supabase project and, if remote preview is needed, a separate protected staging deployment. Verify the target project reference in the dashboard and CLI against the owner-approved staging reference and independently verify it is not production. Do not rely on project name, credentials, or the Vite staging-build guard alone to identify a database. Do not link or write until verified. Never connect a copied production database or use real customer data.
2. Inventory staging migration history and compare it to the reviewed PR SHA, migration ordering, extensions, grants and RLS. Resolve any drift before proceeding. The RPC depends on `production_jobs`, `vendor_id`, `profiles`, the existing RLS policies and `auth.uid()`. Review `20261019135119_vendor_order_projection.sql`, including both normal (non-concurrent) index builds and their possible write locks/cost. No production `db push`, `db reset`, migration apply, or destructive seeding is authorized by this procedure.
3. With an authorized operator, staging-only credentials and explicit approval, visually confirm the linked CLI project reference again, inspect `supabase db push --help` and use its dry run against the linked **staging** project; independently review the pending SQL list before applying only the approved migrations to staging. Do not publish credentials, full connection URLs or environment values in logs. Never use `--include-all` to bypass unexplained history drift. Stop if the target cannot be proven non-production.
4. Use only the staging URL and publishable key with the repository's staging guard. The guard checks the declared production ref but does not verify CLI targets. Ensure `VITE_DEPLOYMENT_ENV=staging`; in CI `PERFUN_STAGING_BUILD=1` is also required. Keep production auth, payment, webhook, shipping and payout settings untouched. Follow the exact documented test-data protections in `STAGING_PREVIEW.md`; do not place passwords in shell history or logs.
5. Verify function grants, `prosecdef=false`, RLS policies and schema-cache discovery in staging. Before migration, the frontend should show the unavailable-server message with retry; after migration/cache discovery, retry should load real staging data. A schema-cache error can also indicate a stale cache; do not infer the migration is absent from that error alone. Rollout requires a separately approved migration-before-frontend plan and a compatible rollback plan.

## Authenticated end-to-end scenarios

Use distinct staging-only Admin, Vendor A, Vendor B and Customer sessions, 375px mobile and desktop. Record timestamp, PR SHA, staging project reference, browser, screenshots with synthetic data only, and results. Never print tokens, keys, recipient details or raw real data.

1. Customer creates synthetic 10 ml + 30 ml and Play Set orders. Admin sees the orders and their real staging statuses. For payment verification use an explicitly configured **sandbox-only** provider and its verified callback; an administratively seeded paid order validates UI only and is not proof of webhook/payment verification. No live DOKU transaction, production webhook, or manually approved production payment.
2. Confirm that verified paid events create one job per item, retries do not duplicate work, and assignment reaches only Vendor A. Vendor B and Customer cannot read the jobs or projection; revoked Vendor access is denied. Test direct RPC authorization as well as hidden navigation.
3. Vendor A sees one Play Set card with three different Top/Middle/Base snapshots and one multi-item card with both sizes and each job's independent status. Create more than 25 orders and test next, previous, first-page refresh and stage changes between pages. Per-request snapshots do not freeze the dataset across requests: record concurrent movement rather than expecting globally immutable pagination.
4. Start and complete each job using real RPC-backed buttons. Check retry, stale server result, double-submit, loading and error recovery. Verify Kirim remains unavailable for the order until **all** its jobs are complete and the server confirms shipment readiness.
5. Decline packing confirmation and verify no `packed` status or audit timestamp is written. Then inspect all five obligations, affirm once, and verify actor/time, backend checklist, shipping guard and legacy shipment history. Do not treat an assertion dialog as physical proof of packing.
6. Verify Copy Address and Copy Order success/failure feedback, all independent formulas, A6 Label and Packing Slip print preview and physical output, long addresses, multi-page output, no clipping and no financial/customer-history leakage. Never print production data.
7. In staging-only shipment data, verify customer-selected courier/service remain locked, admin override remains audited, required tracking/cost/payer validation, confirmation, server status transition and Selesai. Do not enable production shipping or invoke a real shipment. Confirm vendor payout eligibility and reimbursement using the existing read-only operational records; do not modify payout calculation or send real funds.
8. At 375px and desktop verify sidebar/bottom navigation, safe area, no clipped or overlapping content, keyboard/touch targets, loading, empty, unavailable RPC, access-denied and retry states. Save evidence separately from production credentials.

## Query and release gates

Use only synthetic staging data at representative volume. As the staging Vendor role, measure the underlying grouped-page and job-lookup queries with `EXPLAIN (ANALYZE, BUFFERS)` and representative cursors; capture row counts, latency, buffer use and whether the two new indexes are selected. Also measure a large single order, since pagination limits orders, not jobs per order. Do not run `EXPLAIN ANALYZE` on production. Establish an owner-approved p95 target, row volume and index-build window; none has been measured or approved by this procedure.

The cursor accepts the same text domain as `orders.order_number`, including empty and long values. SQL regression covers a long order number at a page boundary. The grouping key assumes each order number has one immutable `ordered_at` across its jobs. Verify that invariant and snapshot history through an appropriately authorized schema/data audit; no such production check was performed here.

GO only after: reviewed migration and deploy/rollback order; isolated staging and schema history verified; CI and staging E2E/RLS pass; representative query plans and index build impact reviewed; authenticated mobile/desktop and A6 reviewed; no live integrations called; and explicit release approval. Any unresolved item is NO-GO. This document does not authorize merging or deployment.
